# R16–R21：变更验证与修复产品路线

日期：2026-09-26。规划基线：`888a753`（文档），最近封存代码基线：`c5c7354`。本文件是新增任务计划，不是实现或远端验收记录。以下任务初始状态均为 **planned**。

## 产品目标与路线恢复

Canary 的下一阶段定位：叠加在现有 CI 上的变更验证与修复工具，服务普通软件项目和使用 AI 编写代码的项目。Agent 评估继续作为一种检查能力。核心采用理由是减少从失败到可核查修复的操作，以及指出本次变更仍未得到验证的范围；这些是待验证的产品目标，尚不是已证明的竞争优势。

主要入口为 GitHub Actions/PR，CLI 负责本地执行，现有页面负责证据下钻与架构地图，结构化接口支持编码 Agent。首批精细支持 Node/TypeScript/JavaScript；其他语言继续使用通用命令检查和文件层级，不承诺同等解析能力。

核对后确认原计划并未全部丢失：R13–R15 的计划、源码和验收仍存在，应保留原编号。当前缺口是总表定位滞后，且已完成的基础能力没有接到上述用户流程。

- **R12：保留并复用。** 已有覆盖/分支/失败地图、原始证据与修复状态。新阶段不重绘大屏。
- **R13：保留并复用。** 已有循环、显式分层违规、耦合观察。提供诊断上下文，不自动证明根因。
- **R14：保留并复用。** 已有固定 Git 基线与潜在影响链。用于验证范围，不等于运行时故障传播证据。
- **R15：保留并复用。** 已有保守增量选择、全量回退和省略披露。减少执行数量的本机例子不能证明普遍耗时收益。
- **R9-03/04：增量扩展。** 已有确定性比较、问题卡、关联重跑。当前“同一检查修复后通过”尚不等于“同一回归测试在修复前失败、修复后通过”。

已有依据：[R13–R15 记录](../evidence/r13-r15-execution.md)、[R9-03/04 记录](../evidence/r9-03-04-execution.md)、`apps/web/src/project-issues.ts`、`packages/improvement/src/project-comparison.ts`、`packages/structure/src/analysis.ts`、`packages/cli/src/project-run.ts`。现有 `.github/workflows/ci.yml` 是本仓库 CI，不能等同于供其他项目使用的 PR 产品集成。

## 实施顺序与范围

按 **R16 → R17 → R18 → R19 → R20 → R21** 推进；每阶段交付可操作的纵向流程，再进入下一阶段。R16–R19 是首个可交付核心，R20 增加长期差异化能力，R21 完成统一交付。

不再增加“小范围试点”作为开发前置条件。功能仍必须有必要的自动化和真实执行验收；fixture 只证明功能，真实用户收益另行记录。R9 的数据和参与者不足不阻塞确定性核心开发，也不能因此标成完成。

首阶段边界：现有 CI 执行用户检查；Canary 整理证据、复现和验证。暂不建设云端任务调度、多租户账户、计费、跨 CI 厂商适配、自治修复机器人、自动提交/合并、复杂模型根因评分。npm 发布、平台二进制和完整供应链工程继续维持既有排除范围；GitHub 接入先采用固定版本源码构建或仓库内 Action。

以下接口与产物名称是设计建议，实施时在对应任务冻结 Schema；本文不将尚未实现的命令列为可用用法。

## R16：统一故障证据包与诊断契约

目标：同一个失败可以直接交给人或编码 Agent，页面、CLI、PR 不再各自解释一份问题。

- **R16-01｜提取公共问题模型。** 将页面内的分类、证据引用和验证关联整理为公共领域逻辑，复用 core/improvement/trace；保持现有问题 ID 和旧 artifact 兼容。定义问题实例与跨运行分组身份，项目身份不得只依赖绝对路径。
- **R16-02｜结构化错误提取。** 首批解析 tsc 诊断、现有命令结果、JUnit 和 Vitest 报告；保留检查/测试名、错误码、堆栈、断言差异、源码位置及原始证据引用。无法解析时保留原日志和 unknown。明确每种报告的支持版本、截断与重复测试名处理。
- **R16-03｜失败分类与保守归组。** 区分编译/类型、测试断言、构建、环境、超时、依赖阻塞与未知；用错误码、规范化位置和显式检查依赖解释归组。相似日志只形成“可能相关”，不能把下游失败隐去或宣称唯一根因。
- **R16-04｜可移交证据包。** 冻结版本化 `failure-bundle`：仓库身份、实际执行 commit、脏工作区标识、run/check/test ID、manifest 哈希、命令 argv/cwd、工具与锁文件身份、缺失环境条件、源码引用和下一步。文本/JSON 共享同一来源；脱敏后再持久化与导出。
- **R16-05｜接入三个现有入口。** CLI 导出、页面问题抽屉、MCP 有界只读查询共同读取证据包。日志内容始终作为待分析数据；包内的命令不因导入或读取而执行。大日志按引用与分页读取。

交付：公共 Schema、解析器、故障证据包、统一问题详情。主要范围：`packages/core`、`packages/improvement`、`packages/trace`、`packages/cli`、`packages/mcp-server`、`apps/web`。

完成标准：一次真实类型/测试/构建失败可以从三个入口定位到同一证据；未知格式、敏感字段、证据损坏、跨项目同名检查、仅日志相似等场景不误归因或误关联。沿用现有原始失败，不修改历史 artifact 来补新字段。

## R17：进入 GitHub PR 与现有 CI 工作流

目标：开发者在已有 PR/Actions 中看到结论，并进入详细证据，不必先打开本地大屏。

- **R17-01｜最小接入契约。** 提供仓库内 Action 或可复制 workflow，固定 Canary 版本。接入两条路径：执行已有显式 Canary 检查；导入现有 CI 生成的受支持报告和执行元数据。外部报告标明来源及验证等级，不能伪造成本地运行器生成的证据。
- **R17-02｜绑定 PR 版本和尝试次数。** 记录仓库、PR、base/head、实际 checkout/merge SHA、workflow/job/matrix、run attempt。旧 SHA 结果不得覆盖新提交结论；取消、重跑与矩阵结果保留各自身份。浅克隆缺基线时给出缺口或保守回退。
- **R17-03｜无需写权限的报告入口。** 先交付 Job Summary、结构化结果与 artifact 上传；失败后仍产出诊断，保留原命令退出码。摘要只展示失败组、验证范围、证据和下一步；提供可下载或离线查看的报告，不把远端链接指向开发者的 localhost。
- **R17-04｜可选 PR 结果发布。** 在仓库允许时发布可更新的 Check/PR 摘要和文件注释，绑定准确 SHA，处理重复事件与注释数量限制。fork PR 无写权限时回退只读产物；写入阶段只处理经过校验的数据，不在带写入凭据的上下文执行不可信 PR 代码。
- **R17-05｜验收和退出路径。** 验证失败、取消、并发新提交、矩阵部分缺失、artifact 丢失和 fork 场景。禁用 Canary 集成后原 CI 可继续运行；Canary 报告失败不能将原测试失败改成成功。

交付：接入模板、摘要/注释发布器、PR 身份契约和离线报告。主要范围：`integrations/`、`.github/`、`packages/cli`、`packages/reporters`、`packages/core`。

完成标准：在已授权的真实 GitHub 仓库中，从 PR/Actions 找到一次实际失败的准确版本、证据和复现入口。本地协议测试通过只标本机验收；远端权限或仓库条件缺失时，远端项明确 blocked，不阻塞 R18 的本地实现。此规划本身不执行远端发布。

## R18：可复现执行与环境缺口说明

目标：把“复制命令”提升为可核查的复现结果，并说明无法恢复的条件。

- **R18-01｜冻结复现说明。** 根据证据包生成源码身份、运行目录、argv、运行时/包管理器版本、锁文件哈希、前置检查、数据 fixture 和环境变量名称清单。密钥值不进入说明；Git 中不可恢复的脏文件/未跟踪文件缺少安全快照时明确 blocked。
- **R18-02｜隔离工作区与生命周期。** 在独立工作区恢复目标版本，保护当前修改；锁定依赖安装方式，保留准备日志、超时/取消和失败后的清理入口。Git worktree 只隔离文件，不宣称提供进程或恶意代码安全沙箱；外部项目代码的执行遵循既有信任边界。
- **R18-03｜执行与结果匹配。** 先准备必需前置项，再执行目标检查。只有同一目标测试/错误证据匹配才标“已复现”；依赖安装失败、服务缺失和另一个测试失败不能算成功复现。
- **R18-04｜显式复现状态。** 至少区分 reproduced、not-reproduced、blocked、inconclusive；记录工具差异、外部服务、数据和凭据缺口。一次未复现不能自动诊断为 flaky；仅提供按需重试，不增加长跑要求。
- **R18-05｜人和 AI 共用操作。** CLI/页面提供先预览后显式执行的入口；MCP 可读取说明与状态，执行权限复用现有受控机制。返回独立 runId、父证据哈希和复现范围，保留原始失败。

交付：复现说明、隔离执行和可解释状态。主要范围：`packages/cli`、`packages/environment`、`packages/isolation`、`packages/runner`、`apps/web`。

完成标准：受支持的本地 Node 项目能复现原错误；缺版本、脏源码不可恢复、错误凭据/外部服务缺失和执行不同失败等情况不会显示“已复现”。验收不要求增加付费模型调用。

## R19：验证修复是否解决原问题

目标：新增明确的修复证据等级，让“重跑变绿”与“回归测试证明原错误已修复”有不同结论。

- **R19-01｜绑定修复候选。** 输入原失败、可恢复的修复前版本、候选版本/补丁、新增回归测试及回归范围；记录源码树/补丁/测试/配置哈希。人和编码 Agent 都可提交候选；不自动修改目标项目或提交代码。
- **R19-02｜同一测试前后执行。** 将完全相同的回归测试分别用于修复前和修复后源码，保存两次环境与执行身份。旧版必须因为目标缺陷而失败，候选版必须通过。旧版无法编译、测试不兼容或依赖变动时不算目标缺陷证据。
- **R19-03｜保留原检查与相关回归。** 在候选上重新运行原失败检查、必需前置项和相关回归；复用 R14/R15 选择解释与保守全量回退。显示执行和省略的检查，验证子集不能代表全项目。
- **R19-04｜检查验证条件是否削弱。** 用有限确定性规则报告测试删除、skip/only、门槛降低、检查移除及配置绕过；记录具体 diff 和规则编号。断言修改只在可靠识别时给出规则发现，复杂语义标需复核。合法测试调整允许具名原因说明，原发现仍保留；不宣称能识别所有绕过方式。
- **R19-05｜修复结论与门禁。** 分别展示重跑通过、前败后过证据、相关回归结果、验证条件变化及未知项。默认报告；项目显式声明的确定性规则才可阻止合并。模型意见不进入硬门禁。保留独立 run/artifact 谱系，不把原失败涂改为通过。

交付：`repair-verification` Schema、双版本验证器、条件变更报告、PR/页面修复结论。主要范围：`packages/core`、`packages/improvement`、`packages/cli`、`packages/policy`、`packages/reporters`、`apps/web`。

完成标准：真修复呈现相同测试“前失败/后通过”；无效补丁、删测试换绿、无关失败、源码/测试哈希错配、候选引入回归分别得到准确结论。既有 R9/R12 的重跑状态继续可读，但不升级为更强证明。

## R20：CI 全绿时的变更验证缺口

目标：解释这次修改验证了什么、还缺什么，并从结论进入地图和源码。

- **R20-01｜接入普通项目覆盖率。** 优先导入 Istanbul JSON 和 LCOV，绑定实际测试执行、源码哈希和工具版本；复用已有 V8 数据。LCOV 缺少分支精确位置等信息时保留缺口，不推导不存在的执行路径。
- **R20-02｜差异覆盖与分母。** 以固定 base/head 计算可映射的新增/修改可执行行和分支，分别显示覆盖/未覆盖/未知、原始分母和匹配来源。删除行、纯格式变更、重命名、生成代码、sourcemap 不匹配分别处理；零分母显示不适用，未采集显示未知。
- **R20-03｜显式行为契约。** 允许维护者声明关键行为 ID、适用路径、对应测试身份和可核查断言/结果。测试名和行执行覆盖不足以证明行为；未提供断言证据只显示维护者关联与测试结果。首版不使用模型猜测业务需求作为合并条件。
- **R20-04｜区分证据种类。** 报告“已执行的变更代码”“有明确契约证据的行为”“未覆盖的可测量代码”“缺少契约验证”“无法判断”。标明单测试关联是否实际采集；聚合覆盖不能推断是哪一项测试验证了某行。
- **R20-05｜PR、地图和门禁一致。** 点击 PR/页面缺口进入对应版本的文件/分支位置，复用 R12 高亮和固定图例。未覆盖与失败分别显示。默认建议；仅维护者显式阈值/契约可设门禁，unknown 的 fail-open/fail-closed 策略必须明示。

交付：覆盖导入器、差异验证报告、行为契约 Schema、地图/PR 联动。主要范围：`packages/coverage`、`packages/structure`、`packages/core`、`packages/policy`、`packages/reporters`、`apps/web`。

完成标准：一个检查全绿但新增路径未覆盖的项目明确展示缺口；源码错版、缺覆盖、只有聚合覆盖和只有测试名关联均不误报行为已验证。对“重复退款”等业务规则，只有显式契约及相应断言证据才支持验证结论。

## R21：统一操作流程与可复现交付

目标：将前五阶段作为一个完整产品交付，记录能够测量的成本和收益，明确尚无外部证据的部分。

- **R21-01｜统一操作导航。** PR 摘要 → 故障证据 → 复现 → 修复候选 → 验证结果 → 变更缺口形成连续路径。页面首页优先问题与验证状态，地图作为下钻入口；沿用现有字体、配色和组件，不重新进行大屏视觉改版。
- **R21-02｜完成编码 Agent 交接。** 复用 R16 的 MCP/JSON，补充有界上下文选择、候选提交身份和验证结果读取；与人操作使用相同契约。项目日志里的指令不能获得执行权限；模型选择和预算由使用者显式配置，Canary 确定性主流程不需要模型。
- **R21-03｜一键验收核心链路。** 固定版本 Node fixture 串起失败、报告、复现、人工或预置候选、前败后过、相关回归及缺口展示；保留原始结果。另验证未知、损坏和验证绕过边界。真实 GitHub 验收单独记录，模拟不能替代远端证据。
- **R21-04｜接入与维护交付。** 更新 README 的产品说明和普通项目首用流程，提供固定版本接入模板、错误排查、旧 artifact 兼容、取消/清理和禁用回退说明。干净 checkout 可重建本机结果；公开宣称的能力与实际验收范围一致。
- **R21-05｜记录收益而不制造成绩。** 保存配置后首次报告耗时、环境准备/排队/执行时间、复现结果、修复验证耗时与模型调用量。人工操作量、诊断准确性和复用意愿只来自真实观察/标签。比较“原 CI + 人工”“原 CI + 直接给编码 Agent 日志”“Canary”时固定同一项目版本、故障、模型预算和环境，报告样本量与失败案例；未开展时显示未测量。

交付：完整指南、可复现验收脚本、阶段执行记录与真实测量字段。主要范围：`scripts/`、`integrations/`、`docs/`、`apps/web` 和既有接口适配层。

完成标准：新使用者能按文档完成核心流程；工程验收与外部产品收益各自显示状态。没有外部用户时可以完成本机核心交付，不能宣布已证明竞争优势。

## 公共契约与实现约束

- **身份链：** repository → base/head/实际执行 commit → workflow attempt/run → check/test → issue → candidate → verification。缺少身份不能依靠同名或最新一条记录补齐。
- **四份扩展产物：** 故障证据包、复现说明/结果、修复验证结果、变更验证报告。复用现有 manifest/哈希/谱系与脱敏路径，不新增独立存储系统。
- **证据边界：** 事实、静态潜在影响、规则发现、维护者声明和模型推断分开；完整性校验只证明封存后未变，不能证明外部报告内容真实。
- **执行边界：** 默认确定性、默认完整检查；增量选择继续显式启用。取消、预算、执行权限和日志目录沿用既有机制，不引入后台常驻模型任务。
- **旧数据兼容：** 缺少新 Schema 的历史运行显示该能力不可用；不重新读取当前源码来填充旧结果，也不把 legacy 结果自动升级为修复证明。
- **回退：** 每阶段可独立禁用新导入器、PR 发布或门禁；现有 run/report/完整检查继续工作。保留用户历史证据。

## 每一小步的复核与状态更新

任务开始核对基线 SHA、工作树和已有能力。任务结束在阶段执行记录写入：预期用户行为、实际变化、验证命令/原始证据、未覆盖范围、回滚方式，以及以下复核结论：

1. 是否帮助用户回答问题在哪里、如何复现、修复是否成立或哪里没有验证？
2. 是否复用了 R3/R9/R10–R15，避免维护第二套证据、地图和运行器？
3. 是否出现把推断当事实、子集当全量、覆盖当行为正确、测试变绿当修复证明的情况？
4. 是否无意引入云平台、付费模型、长跑或未经授权的外部操作？
5. 实现和相关验证都完成后才改为 completed；外部缺输入为 blocked；用户明确延后为 deferred。

本轮只恢复和编排任务，R16–R21 全部保持 planned。首个实施任务是 **R16-01**。R6 原生 Ubuntu/macOS 与 R7 长跑继续 deferred；R9-02 真实故障配对、R9-05 独立用户与 Judge 校准继续 blocked。这些外部结果决定未来能够作出的产品声明，不作为本轮确定性功能的强制等待条件。
