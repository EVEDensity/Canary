# 进化策略：硬规范、默认软进化、硬进化显式授权

> 状态：待实现的工程安全目标。替代原 `AGENT-SELF-EVOLUTION-TARGET.md`，与[自循环设计](agent-loop.md)配套。不是现在可加载的配置，也不是本次任务的代码写入授权。

## 两个独立开关

| 维度                  | 默认目标 | 可选目标             | 含义                                              |
| --------------------- | -------- | -------------------- | ------------------------------------------------- |
| 修改对象 `mode`       | `soft`   | `hard`               | 软：受管理经验/任务策略；硬：另外允许授权源码路径 |
| 执行方式 `activation` | `manual` | `auto_within_policy` | 人工触发/确认，或在有限授权内自动循环和激活       |

上述名称是**设计术语**，不是已实现的 CLI 参数或配置 Schema。

- soft + manual：人工请求分析和候选，验证后人工激活。
- soft + auto：控制器在授权范围内自动迭代经验，不能改项目源码。
- hard + manual：可产生并验证代码候选，应用前需确认。
- hard + auto：所有门禁满足且授权仍有效时，受信应用器可自动修改本地授权代码。不是无限自治，push/部署仍需单独授权。

“开源项目”并不天然允许写其上游。只有用户拥有的仓库、fork 或明确授权的工作副本才能进入硬模式。

## 强约束必须在哪里执行

自然语言规则负责说明意图；Schema 负责拒绝错误格式；策略引擎负责动作准入；OS/容器等真实隔离负责阻止绕过；独立应用器负责发布。这几层缺一不可。当前 Node worker 只提供进程级执行管理，**不是上述安全隔离**。

如果用户把 Canary 作为 Skill 接入一个仍拥有任意 shell 和全盘读写权限的 Agent，Canary 只能限制自身接口，不能保证那个 Agent 不从其他工具绕开。需要宿主提供可靠限制，或改由 Canary 控制的隔离执行器运行候选。未能建立边界时，只提供建议/人工应用，不开放自动硬进化。

## 不可由候选修改的硬规范

| ID     | 规范                                     | 强制位置                           | 最低拒绝测试                                  |
| ------ | ---------------------------------------- | ---------------------------------- | --------------------------------------------- |
| POL-01 | 目标与验收不能被候选自行重写             | 外置版本化策略、只读注入           | 改阈值/删除失败用例仍被拒绝                   |
| POL-02 | 保护评估器、保留集、控制器和授权记录     | 不挂载/只读挂载、独立进程身份      | 路径穿越、符号链接、硬链接/别名越界测试       |
| POL-03 | 文件/工具/网络最小权限，禁止环境密钥继承 | 沙箱权限、环境 allowlist、出网代理 | 读父目录/密钥、连未授权域名被阻断             |
| POL-04 | 只有完整且可比的试验能进入质量比较       | 独立评估服务                       | 缺 case/trial、重复 ID、取消/崩溃不能 improve |
| POL-05 | 安全/状态/必需质量门禁不能用总分抵消     | 固定决策器                         | 质量增益但越权，必须拒绝                      |
| POL-06 | 提案不能批准自己，证据不能由候选覆盖     | 独立存储写权限与审批角色           | 伪造 report/approved 字段无效                 |
| POL-07 | 有限轮次、费用、时间、工具调用；可取消   | 受信预算账本与调度器               | 并发候选合计超额被阻断                        |
| POL-08 | 激活精确已验证版本，不覆盖用户新修改     | 应用器哈希与基线版本检查           | 验证后换文件/基线漂移不能应用                 |
| POL-09 | 记忆是数据，不得提升低信任指令           | 经验加载器与安全检查               | 恶意 Trace 要求忽略规则不能激活               |
| POL-10 | 可审计、可撤销、有回滚界限               | 不可由候选改写的事件记录           | 撤销后排队补丁不生效，恢复不重复应用          |

保护路径要先解析到实际目标，再校验范围；不能只按字符串前缀判断。目录白名单也不能防住允许路径中的恶意代码或构建脚本，因此隔离执行和独立测试仍必需。负例中预期的 policy/loop 事件可用于评价测试结果，但**不能豁免真实访问控制**。

## 授权最小内容

授权记录至少绑定：主体、项目身份、基线范围、允许对象/路径/动作、保护对象、网络和工具能力、预算、有效期、批准方式及撤销标识。更改授权只能通过用户/受信管理面，Agent 不能修改本地配置来提升自己的权限。

不隐式继承 IDE 登录态；不记录原始凭证；不通过模型推测授权。API 调用、本地模型启动、外发数据、后台常驻以及部署均需要各自明确的许可范围。

## 失败策略

- 缺少必需评估器、指标不可用、证据不完整、授权过期/不明：停止准入，显示原因。
- 没有可用模型：基础确定性运行继续；需要模型的进化阶段等待，不伪造评价。
- 自动硬模式发生隔离能力缺失：拒绝启动；不能静默切到无隔离写文件。
- 任何拒绝都不会通过“再问一次模型”扩大能力。
- 回滚恢复受管理版本，不声称撤销外部现实状态；事故处理与安全修补另走人工审查。

## 实施原则

先把这些规则落实为独立的拒绝测试，再开放对应动作。规则文档不是安全证明；每个支持平台必须提供边界验证结果。具体任务见[评估可信度](../roadmap/02-evaluation-integrity.md)、[软进化](../roadmap/03-host-and-soft-evolution.md)与[硬进化](../roadmap/04-controlled-hard-evolution.md)。
