# Canary 下一阶段评估与建议

日期：2026-09-25。性质：研究与建议，不自动替换 R0–R8 已批准路线图。依据：本地源码、路线图、已有验收记录及下列官方资料；本轮未重新执行完整测试，也未验证远端 CI 当前状态。数字目标均为建议的试点验收条件，不是行业标准或已取得成绩。

## 当前判断

Canary 已形成可运行的本地 Agent/项目验证工作台，工程闭环较完整，适合进入外部试用 Alpha。现有证据不足以称为行业顶级或全面生产就绪；主要欠缺在真实场景效用、评估可信度、外部使用反馈和公开可复现交付。

- R0–R5：按已有记录，在 Windows 指定环境内完成运行器、配置诊断、证据链、项目门禁和报告流程。全局安装表示任意目录可调用，执行范围仍是选定项目；它不自动扫描全机仓库或触发远端 CI。
- R6：Windows 与 Ubuntu 容器有固定版本证据；Pi 有固定运行时和一次受限真实推理。macOS、原生 Ubuntu 的当前验收仍缺失，历史平台证据不能直接证明最新 R8 工作树兼容。
- R7：日志整理和初步维护完成；长跑、容量和真实重启实验暂缓。这符合此前范围，但进入生产使用前需要按使用规模补验。
- R8：候选、选择、对比、批准、激活、回滚和 Skill 草稿形成固定函数 Agent 闭环。当前改动仍未提交，HEAD 为 `77f34f0`，因此还没有可供外部用户准确复现的 R8 交付 commit。

已有全仓检查成功记录见 `docs/evidence/r8-05-09-execution.md`。内部测试通过说明实现满足所测契约，不等同于用户获得价值。

## 五个关键差距

1. **经验效用尚未证明。** `packages/cli/tests/r8-closure.test.ts` 的 Agent 根据 `ctx.experiences.length` 决定是否返回成功结果，没有读取建议正文。它证明编排与权限路径，未验证建议是否正确、相关或有效。下一批试验必须让无经验、相关经验、无关经验、错误经验产生可区分的结果，并独立验证实际任务终态。
2. **评估统计仍薄。** 已有 repetitions、比较和 HTTP Judge 接口；此次检索未发现通过率置信区间、配对效应区间或 pass@k/pass^k 的实现。Judge 自报 confidence 与跨任务统计置信区间含义不同。重复同一个简单任务也不能当成大量独立任务证据。
3. **文档与入口存在漂移。** README 仍有 Pi 未验收和旧五视图表述，与 R6/R8 当前记录不一致。项目面板和控制面分别有独立入口，用户从失败跳到经验批准的连续路径需要重新验证。
4. **差异化已有基础，外部证据不足。** manifest、哈希、谱系、隐私与精确回滚值得保留；哈希校验只能证明相对于所信任清单的完整性，不能单独证明业务正确、建议有效或对恶意改写者的身份真实性。
5. **产品验证尚缺。** 当前仓库材料不足以确认外部团队独立接入成功率、持续使用、误报/漏报和诊断耗时改善。不能据此推断实际没有用户，但不能把这些能力算作已验收。

源码覆盖率也应继续与任务成功率分开：执行过代码不等于完成用户目标；HTTP/MCP 黑盒不应显示未采集的源码覆盖率。下一阶段可增加任务、工具契约和故障模式的覆盖清单，但其分母必须明确。

## 官方资料带来的定位判断

- [Promptfoo 的 CI/CD](https://www.promptfoo.dev/docs/integrations/ci-cd/) 已覆盖评估、红队测试、质量门禁和报告。仅提供 CLI、通过率与网页难以形成有力差异。
- [LangSmith Evaluation](https://docs.langchain.com/langsmith/evaluation) 将真实轨迹转为数据集，支持离线/在线评估、人工/代码/模型评分及版本比较。Canary 应优先打通真实故障到固定回归用例的低成本路径。
- [Braintrust 实验比较](https://www.braintrust.dev/docs/evaluate/compare-experiments) 支持逐例差异、人工成对判断，以及质量、耗时、成本等汇总。Canary 的页面应帮助用户判断某次变更是否可接受，并可下钻到证据。
- [Inspect](https://inspect.aisi.org.uk/) 将 dataset、solver、scorer 分离，提供工具与沙箱；[评分文档](https://inspect.aisi.org.uk/scorers.html)包含标准误差和聚类统计方向。Canary 的运行完整性优势需要配合评估方法本身的可靠性。
- [Anthropic 的 Agent 评估实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)建议从真实失败任务开始，区分能力测试与回归测试，并强调模型评分应经人工校准。文中给出的 20–50 个起步任务和重复运行指标，为小规模开始提供参考，不构成通用统计充分性保证。
- [Langfuse 评估](https://langfuse.com/docs/evaluation/overview)也覆盖评估工作流。是否采用云端或自托管，不能单独承担 Canary 的全部差异化。

这些产品能力来自官方文档，不是本轮横向实测排名；没有依据宣称 Canary 在功能、性能或市场上领先它们。

## 建议的主线

先服务使用本地编码 Agent、MCP 工具和项目 CI 的个人开发者及小团队：让一次变更能被检查、定位、重现、验证和追责。项目检查验证代码与环境，Agent 检查验证行为与终态，证据链把它们连接起来。

建议定位：**面向 Agent 变更的本地优先质量门禁与可复现故障诊断。** 竞争力应来自接入成本低、结果可信、定位速度快、证据可带走。受控经验与 Skill 是这条流程的增强能力，其优先级取决于真实效用验证。

## 建议 R9：外部项目可用性与评估可信度

### R9-00 可复现交付与文档收口

整理并提交当前 R8 改动，记录准确 commit、依赖和证据；同步 README、实际命令、页面与支持矩阵。为干净 checkout 明确先构建再测试的顺序，避免测试误用旧 dist。先使用 Git checkout 试用即可，暂不恢复此前排除的 npm 发布和签名制品任务。

验收：外部用户能从一个 commit 重建已声明支持的本机结果；安装、首次配置和证据位置有一份准确指南。

### R9-01 三个外部项目的最短接入路径

选择真实 Node/TypeScript 工具 Agent、Python HTTP Agent、MCP 工具项目各一个；Python/黑盒的覆盖能力如实声明。复用已有发现/配置能力，只有发现明确阻力时才增加初始化向导。

建议试点目标：项目依赖已安装时，首次得到真实失败或成功报告在 15 分钟内；逐项记录人工改配置次数与失败原因。这个时间目标需要实测，不作为已有承诺。

### R9-02 真实故障到回归数据集

先整理 20–30 个授权使用的真实失败任务，覆盖错误参数、工具失败、状态未落盘、重复副作用、超时恢复、结构错误及与当前产品相关的注入攻击。保存项目/任务/评估器版本、来源、成功终态、修复前后版本和可重现方法。人工确认的数据集与探索集分离，保留 holdout。

验收：至少 10 对真实失败/修复版本能独立复现；同时提供正确行为对照和已知漏报。不能通过在 Agent 中硬编码“收到经验就成功”来证明收益。

### R9-03 评估可信度与受控成本

先用代码断言验证终态、副作用和工具契约，主观部分才启用 Judge。固定评估器、rubric、模型/配置与版本，保留少量人工标注和分歧记录。按任务做配对比较；对波动场景重复执行，展示样本量、分母、失败分布及适当的不确定性区间。样本不够时给出“证据不足”。

成本策略：确定性检查默认零模型调用；模型试验逐次设调用数/token/费用预算，仅对选中任务执行。缓存应记录命中，不能算作独立重复试验。相同 seed 也不能保证远端模型逐字重现。

### R9-04 统一诊断与发布决策

在已有面板中把“失败检查 → case/tool/文件位置 → 对应证据 → 重现命令 → 修复后重跑 → 比较结论”串成一条路径。保留明确的通过、阻止、证据不足状态。收益与新增回归并列显示，按具体指标展示耗时和已知 token/费用；未采集指标继续显示 unavailable。

验收：用户从一个失败可直接取得重现方法，修复后能看到相同任务的前后差异；项目面板到受保护操作入口不丢失 run/check/case 身份。

### R9-05 小规模外部试用

建议招募 3–5 位目标用户进行两轮独立试用，记录首次成功运行时间、问题定位时间、误报/漏报、真实发现的问题及是否主动再次使用。报告实际原始数值与样本量。5 位用户不足以证明市场成立，但能暴露关键接入与理解问题。

退出条件：三个项目有可复现案例；至少出现作者未预设的有效故障发现；用户能独立完成重跑与诊断。若达不到，优先修流程，不扩大 provider/插件数量。

## 后续顺序与资源取舍

第一个短迭代只做 R9-00、R9-01 和 R9-02 的前 10 个任务；这一阶段可以不产生模型费用。确定外部用户确实能得到价值后，再做 R9-03/04 并同步试用。以上按验收门推进，不预设必须在两周内全部完成。

R10 再处理开源后的三平台远端 CI、与试点规模对应的恢复性/容量测试、公开可复现基准及稳定扩展契约。若导入/导出标准能降低用户接入成本，再提供明确版本的兼容层；不扩展成全量可观测平台。

R11 再评估受控经验的真实内容收益：正确经验应改善目标任务，无关或错误经验不应被错误批准，holdout 不退化，收益能够复验。多模型大赛、自动批准、自动源码修改、常驻进化和远端市场继续延后。

“行业顶级”应通过同一组代表性任务上的接入时间、故障检出、误报、诊断耗时、运行成本与可复现性进行公开比较，并由独立使用者复验。Canary 可以先在本地 Agent 变更验证这一窄领域做到可信赖，再扩展覆盖范围。
